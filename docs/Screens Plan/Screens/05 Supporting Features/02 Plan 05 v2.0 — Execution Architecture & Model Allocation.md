# Plan 05 v2.0 — Execution Architecture & Model Allocation

I would execute Plan 05 as **five feature waves plus an independent Zone Foundation track**, with Wave 4 hard-blocked on the Zone Gate and Wave 5 acting as release integration rather than another feature-development wave.

This follows the plan's authoritative sequencing, but I would make the **model allocation more deliberate than simply assigning one model per wave**. Plan 05 contains several distinct risk classes: transactional backend work, scheduling/state-machine work, geo infrastructure, mobile UX, and mechanical verification. Those should not all consume the same model tier.

The plan explicitly establishes Wave 0 → Waves 1–3 → Zone Gate → Wave 4 → Wave 5, with the Zone Gate running in parallel with Waves 1–3.

# 3. Wave 0 — Foundation

The canonical plan defines Wave 0 as blocking everything. It covers dependencies/dev build, theme tokens, `ErrorBanner`, `OfflineIndicator`, `EmptyState`, i18n, root tracking exemption, time helpers, feature flags, and the first G-1 audit. Exit requires the components to be importable and `tsc ×2 + lint` to pass. 

### Execution units

| Unit | Work                                  | Model             |
| ---- | ------------------------------------- | ----------------- |
| W0-A | Dependencies + dev-build verification | DeepSeek V4 Flash |
| W0-B | Theme tokens + Pattern A verification | DeepSeek V4 Flash |
| W0-C | ErrorBanner + OfflineIndicator        | GLM-5.2           |
| W0-D | EmptyState reuse/restyle              | DeepSeek V4 Flash |
| W0-E | i18n foundation                       | DeepSeek V4 Flash |

| W0-H | Feature flags                         | GLM-5.2           |
| W0-I | G-1 reference audit                   | MiMo 2.5          |

### Why GLM-5.2 here?

Wave 0 establishes shared contracts that every later screen will consume. It is not appropriate for DeepSeek to independently invent these patterns.

However, **GLM-5.3 is unnecessary**. The requirements are explicit and the architectural risk is manageable.

### Wave 0 review

Use **MiMo 2.5**, not GLM-5.3.

Review specifically for:

* duplicate `EmptyState`;
* incorrect theme handling;
* `console.log`;
* `any`;
* wrong i18n source;
* incorrect time-zone handling;
* incorrect feature-flag caching;
* missing cleanup;
* dependency/version mistakes.

# 7. Zone Foundation — separate engineering track

This is the most important architectural track in Plan 05.

The plan identifies the existing single-zone restrictions and defines Z-1 through Z-8 to move the system toward multiple active zones. 

I would allocate this work much more aggressively than ordinary screens.

---

## Z-1 — Migration M1

### Model

**GLM-5.3**

This is a database foundation change.

It removes the single-active-zone unique index and introduces:

* active-zone index;
* forecast uniqueness;
* ride zone/time index.

The migration is index-only, but it changes a fundamental invariant.

### Review

**Qwen Coder** independently.

This is exactly where Qwen's technical dependency auditing is valuable.

Ask Qwen to inspect:

* all queries relying on single-active-zone semantics;
* indexes;
* query plans;
* migration safety;
* existing assumptions in `lib/zone.ts`;
* rollback.

---

# 8. Z-2 / Z-3 — Zone resolution

### Z-2

`getZoneForLocation()` becomes multi-zone aware, with polygon normalization, ordered point-in-polygon checks, cache invalidation, and zero-zone behavior.

### Z-3

Remove sentinel writes.

### Model

**GLM-5.3**

These two should be treated as one logical implementation unit because Z-3 depends directly on the new Z-2 semantics.

### Review

**Qwen Coder**

Qwen should independently trace every caller and identify any remaining assumptions that a single zone exists.

# 9. Z-4 — Driver zone resolution

This deserves another **GLM-5.3** call.

The hysteresis requirement is subtle:

* three consecutive heartbeats in a new H3 cell;
* only then commit zone change;
* forced re-resolution every 10 minutes.

That is explicitly intended to solve GPS drift while still catching boundary changes. 

### Review

**Qwen Coder + MiMo Pro**

* two active zones;

* forecast rows;
* heatmap data;

* root and `utils-server` TypeScript;

# 26. The key strategic point

The biggest mistake would be to treat Plan 05 as **"59 features to implement."**

It is actually approximately:

**4 different engineering programs:**

1. **Scheduled-ride/cancellation state machine**
2. **Rider safety/support**
3. **Multi-zone geo/forecast foundation**
4. **Driver feature/UI integration**

with shared foundation and release integration around them.

The **multi-zone foundation and scheduled-ride/cancellation system are the two places where I would spend the majority of the high-end reasoning budget**.

Everything else should be pushed toward GLM-5.2, DeepSeek, MiMo, and targeted Qwen review.

That is the allocation most consistent with the stated objective of maximizing **correct completed software per rate-limit window**, rather than minimizing expensive model calls. 

### Recommended execution order

**Authorize and execute:**

1. **Wave 0**
2. Start **Wave 1 + Wave 2 + Wave 3 + Zone Track in parallel**
3. Complete **Zone Gate**
4. Execute **Wave 4**
5. Execute **Wave 5**
6. Run **MiMo Pro independent review**
7. Run **GLM-5.3 final skeptic**
8. Resolve findings
9. Final mechanical gates
10. Release

The next artifact should therefore be the **individual Kilo Code implementation prompts for Wave 0**, not prompts for the entire plan at once. This preserves the dependency boundaries and lets us inspect the actual repository state after each high-risk implementation before authorizing the next one.
