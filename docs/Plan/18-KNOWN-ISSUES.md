# Known Issues & Tech Debt: Ride

## How to use

| TD-01 | SMS receiver | Android OEM battery optimisation (Samsung, Xiaomi, Oppo, Vivo) kills the BroadcastReceiver for incoming SMS before it can write to RTDB. Affects an estimated 30–60% of Android devices in Bangladesh. | high | Manual OTP entry fallback shown after 20s timeout. User reads SMS manually and types the code. | If manual entry rate > 50% of all verifications, implement OEM-specific prompts to disable battery optimisation at first launch. |
| TD-02 | bKash integration | bKash Merchant API v1.2.0-beta sandbox does not always send payment callbacks within the documented 5-minute window. Callbacks arrive up to 30 minutes late in sandbox. | med (sandbox only) | Auto-query `bKash.queryPayment()` after 5-minute timeout. Works correctly. Production bKash callbacks are reliable. | If production callback latency > 2 min for > 5% of payments post-launch. |
| TD-03 | H3 index | The in-memory H3 driver index in utils-server is a plain JavaScript `Map`, not a spatial index. At current MVP scale (single Dhaka zone, < 5,000 drivers), performance is acceptable. Above 10,000 concurrent drivers, linear scan will degrade. | low | Not needed at MVP scale. | When concurrent online driver count consistently exceeds 5,000. Switch to Redis HASH or PostgreSQL `ST_DWithin` for driver lookup. |
| TD-04 | Scheduled rides | The scheduler for dispatching scheduled rides runs as a `setInterval` inside utils-server. If utils-server restarts, in-flight scheduled ride timers are lost. Rides scheduled for the next restart window will not dispatch. | med | At utils-server startup, query DB for any scheduled rides with `scheduled_at BETWEEN now() AND now() + 60 min` and re-register their timers. This query exists but has a 5-second startup delay — rides scheduled during this window could be missed. | Any complaint from a rider that their scheduled ride was not dispatched. |
| TD-05 | Daily call reset | `subscriptions.daily_calls_used` is reset at midnight BDT by a cron job in utils-server. The reset is not atomic with call deduction writes. Under heavy load at exactly midnight, a race exists where a deduction reads `daily_calls_used` before the reset increments it. | low | **Mitigated:** Daily reset now embedded in the deduction transaction via CASE WHEN daily_reset_at <= now() in 02-ARCHITECTURE.md. The standalone cron job remains as a fallback for idle drivers. The race window is now limited to drivers who receive their first offer of the new day in the exact same millisecond the cron fires. | When unlimited-package daily-cap complaints from drivers exceed 1/week. |
| TD-06 | Nagad integration | Nagad Merchant API sandbox credentials are not publicly available — must be requested directly from Nagad and approved (5–15 business day wait). bKash is primary; Nagad is a secondary option listed in the UI but not testable until credentials are approved. | med | Ship with bKash only at MVP; Nagad payment option shown as "Coming soon" in package purchase screen until credentials received and tested. | Nagad credentials received and sandbox integration tested end-to-end. |
| TD-07 | Admin auth | Admin panel uses the same Firebase phone auth as drivers/riders, with an additional `users.role = 'admin'` check. There is no separate admin credential or MFA. If an admin's phone is compromised, the attacker gains admin access. | med | No workaround — treat admin phone numbers as high-security credentials. Store them privately. | Post-MVP: add TOTP (Google Authenticator) as a second factor for admin logins. |
| TD-08 | Document presigned URLs | Firebase Storage presigned URLs for admin document review are generated with a 15-minute TTL. If the admin review takes longer than 15 minutes on a single document (e.g., cross-checking with external registry), images will fail to load and require a manual page refresh. | low | Page refresh triggers new presigned URL fetch automatically (handled in `AdminDocumentViewer.tsx`). | If admin review time consistently > 15 min per driver, increase TTL to 60 min. |
| TD-09 | ~~Owner consent OTP~~ RESOLVED | ~~The vehicle owner consent OTP uses Firebase standard SMS auth.~~ **RESOLVED:** Owner consent is now document-based (scan copy upload via `POST /api/driver/owner-consent/submit`). No OTP is sent to the vehicle owner. The consent document is uploaded and reviewed by admin. This eliminates the Firebase Phone Auth PII concern for third-party phone numbers entirely. Owner phone number is stored in `owner_consents` table on BD-localized PostgreSQL only — no data sent to any third-party service. | **RESOLVED** | n/a | n/a |
| TD-10 | Compensation queue in-memory | `compensationQueue` was an in-memory array in utils-server. If utils-server crashed with items in the queue, those queue items were lost. **RESOLVED** by TD-17: replaced with `compensation_queue` DB table. | **RESOLVED** | n/a | n/a |
| TD-11 | utils-server scaling | `connectedDrivers` and the H3 index are in-process maps. If Railway scales utils-server to >1 replica, both instances will dispatch the same ride and double-attempt deductions (the unique index prevents double-charging but causes 50% offer loss). | high (post-MVP) | Set `replicas=1` in Railway config. Document in 15-RUNBOOK-DEPLOY.md. | When concurrent online drivers > 5,000 or HA SLA required. Switch to Redis or PostGIS for shared state. |
| TD-12 | RTDB verification cleanup | The cleanup scheduled function runs every 30 minutes, but verification sessions expire after 60 seconds. Up to 30 minutes of garbage nodes may accumulate. Under attack traffic, RTDB could hit the 10K node threshold (17-MONITORING.md). | low | Accepted at MVP scale. Increase cleanup frequency to 5 min if ≥ 10K nodes seen. | Monitoring threshold breach on RTDB node count. |
| TD-13 | Trial enforcement DB-level | The trial-already-used check in P5-05 is a read-then-write pattern. Concurrent purchases by the same driver could each pass the check before either writes. | med | Mitigated by the partial unique index on `subscriptions(driver_id) WHERE is_trial=true AND status IN ('active','expired')`. A concurrent second purchase will receive a unique constraint violation. The handler must catch this violation and return 409 `trial_already_used` — NOT a 500. | n/a |
| TD-14 | **[Superseded by ADR-017 — Supabase Auth handles OTP verification internally; no RTDB receipt writes or anonymous UID binding needed]** HMAC auth anonymous UID binding | The `checkAuth` CF mints a custom token for a auth_uid derived from the phone number. The RTDB receipt write is authenticated via anonymous Firebase Auth. If an attacker creates an anonymous session and writes a spoofed receipt for a victim's sessionCode, they could hijack the auth. | **high — must fix before production** | The CF should store the anonymous UID in `verification_requests/{sessionCode}/initiator_uid` at startVerification time, and validate in checkAuth that the RTDB write came from the same UID. Add RTDB security rules that only allow writes to `verification_requests/{code}/receipt` from authenticated UIDs matching the stored `initiator_uid`. Until this is implemented, rate limiting (5/phone/10min) partially mitigates. | Before production launch. |

| TD-17 | Compensation queue persistence | `compensationQueue` is an in-memory array (TD-10).
